Adding roles and renaming them

Admins add a role from the permissions page, start it from an existing role's permissions, and rename any role except Admin. People keep their role through a rename. Deleting a role first moves its people to another role.

4 · What it takes under the hood

1
Roles move from a fixed list to a tableToday the five roles are written into the code and the database only accepts those. They'd become rows: a permanent key (never shown, never changes), a name, a description, an order, which role it started from, and whether it's built in. Existing users keep their roles; a migration creates the five built-in rows.
2
Renames change the name, never the keyUsers and permissions point at the key, so a rename touches one row. That's why "Sales rep" → "Account Executive" can't break anything.
3
Code stops checking role namesThe few places that test for a specific role go through permissions instead. Admin keeps its fixed key (admin). The price check's "Route to RevOps" becomes "route to someone who can approve tier 1", which the approval workflow needed anyway.
4
Defaults for future permissionsWhen a new feature adds a permission, each built-in role gets its listed default and each custom role gets the default of the role it started from (or Off if it started from nothing).
5
GuardrailsAdmin can't be renamed or deleted. A role with people can't be deleted until they're moved. Names are unique. A cap of 20 roles keeps the matrix readable.

5 · Decisions

  1. Can built-in roles (Sales rep, RevOps, VP Sales, CEO) be deleted, or only renamed?Recommended: renamed and deleted like any role once nobody has them. Only Admin is protected.
  2. Can Admin be renamed?Recommended: no. It's the one role the app depends on by name.
  3. New permissions on custom rolesRecommended: inherit the default of the role it started from, as shown.
  4. Who manages roles?Recommended: admins only, the same as the matrix.
