2 · How the approval gates work

Approvals are checked the whole time you edit, but only stop you at two points: sending a proposal and requesting an agreement. Each approval is attached to a version, so the prospect never gets terms nobody signed off on.

Lifecycle

1
Rep edits termsGuardrails run live. Findings show next to the field that tripped them, with who would need to approve.
2
Rep clicks Send (or Request agreement)Nothing tripped: it goes. Something tripped: Send is locked and becomes "Request approval".
Clean → sendsNeeds approval → request
3
Request goes to the right personThe lowest role that can approve every item gets an in-app notification and a Slack message with Approve / Reject buttons. The rep adds a reason ("competitive with X, 3-year commitment").
4
Approved → that version is approvedSend unlocks. Rejected → the rep sees the note and adjusts. Every decision is kept in the deal's history.
5
Later changesRecommended: changes that make terms better for Teton (or don't touch an approved rule) keep the approval. Making an approved item worse, or tripping a new rule, asks again for that item only.

4 · Build order

Ordered by dependency first, then value. Approvals need roles (who can approve). Stages and queues are mostly glue on top of what exists. Integrations go last because each step works manually first.

✓

Already in place

Deals and versions, terms and the price book, guardrail findings (warnings), business case formatting and templates, deal room and tracked sharing, prospect comments and questions, Scope Mode, version diff, tasks and notifications, the prospect's "Request agreement" button. User roles exist (rep, Deal Desk, VP Sales, CEO, admin), and an empty approvals table was set up early.

Steps covered: 1, 3–7, 9
1

Roles & permissions

Already first on the backlog. Decides who can approve what, who sees which deals, and who edits the price book.

  • Capability matrix per role, admin-editable, checked on the server
  • "Can approve" capabilities per rule and tier
Unlocks: approvalsSize
2

Approval rules in the price book

Move the fixed guardrails into admin settings and add the missing ones.

  • Price, service term, pilot length and pilot cost, each with tiers and an approver
  • Live findings on the deal page, next to the field
  • Re-run every saved deal against new rules (no surprise lockouts)
Needs: 1Size
3

Approval workflow

The core of what you described: the biggest piece and the most value.

  • Request with a reason → approver notified → approve / reject with a note
  • Send and agreement request locked until approved; draft-marked PDF still allowed
  • Approval attached to a version; re-approval only for items that got worse
  • Approvals inbox and history on the deal
Needs: 1, 2Size
4

Deal stages + estimate vs scoped

The pipeline band from section 1, moving itself from events the system already records.

  • Stages: Draft → Estimate sent → In review → Scoping → Scoped proposal sent → Agreement → Signature → Won / Lost
  • "Estimate" flag on the proposal until scoped; a "what changed" note when the scope lands
  • Deals list filtered and grouped by stage
Needs: nothing (can run alongside 1–3)Size
5

Scoping handoff

Steps 8–9 as a queue instead of a Slack message.

  • "Request scoping" on the deal (and plan upload on the prospect's shared link)
  • RevOps queue: claim, due date, done → rep notified and the deal leaves "Estimate"
Needs: 4Size
6

Agreement request + tracker, posted to Slack

Steps 11–16 recorded in one place. Builds on the agreement request the prospect can already send.

  • Rep form pre-filled from the approved version (entity, signer, scope, terms)
  • Posts to the agreement Slack channel; RevOps agreement queue
  • Tracker: drafts and redlines uploaded per round, leadership comments, who has the ball
  • Slack Approve / Reject buttons for approvals (from phase 3)
Needs: 3; a Slack app for the channelSize
7

DocuSign (optional)

Until then, RevOps clicks "Sent for signature" and "Signed". With it: send from the deal, and the deal moves to Won when both sides have signed.

Needs: 6; a DocuSign API accountSize

5 · Decisions before building

  1. Does an approval lock sending, or only warn?Recommended: lock Send and the agreement request; allow a PDF marked Draft for previews.
  2. The thresholds and tiers in the rules tablePrice, term, pilot length, pilot cost: the numbers and who approves each tier. Also whether CEO is ever required, or VP Sales is the top tier.
  3. When does a change need re-approval?Recommended: only when an approved item gets worse or a new rule trips. Better terms keep the approval.
  4. Slack: post only, or approve from Slack too?Posting needs a simple webhook. Approve / Reject buttons need a Teton Slack app; it's more setup but saves approvers a click.
  5. Estimates: does anything change for the prospect?Recommended: an "Estimate based on room counts" note on the proposal until the deal is scoped.
  6. DocuSign now or later?Recommended: later. Manual "sent / signed" buttons first.
